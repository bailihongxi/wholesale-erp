# 家电批发 ERP · 性能优化方案（2026-09-25）

> 目标：手机端 / 电脑端浏览、查询、编辑、删除、做单、切页都要即时反馈，不能有可感知延迟。
> 约束：不改数据库表结构、每一步可独立回退、不产生需要人工收尾的坑。

---

## 〇、结论先行

当前慢，**不是因为网络慢，也不是因为手机慢**，而是三个原因叠加：

| 根因 | 量化事实 | 影响 |
|---|---|---|
| **① 请求次数爆炸** | 老板工作台一次要发 **20+ 个请求**，其中应收/应付是 **2×N 串行 N+1**（每张单一次请求） | 每个请求都有一次跨境 RTT（新加坡，200~400ms），500 张单 = **50 秒以上** |
| **② 没有本地持久化缓存** | `src/db/` 里 **0 处 `new Dexie`**，依赖装了但本地库根本没启用；缓存只有「内存级」（刷新即失） | 每次打开页面、每次切页都重新全量拉云端 |
| **③ 首屏单包 + 切页重跑** | 首屏 `index.js` **496KB / gzip 156KB 单文件**；25 处 `useReloadOnActivate` 切回页面整份重拉 | 首屏 3~5 秒；切页等于重跑首屏 |

**修复优先级（收益/风险比）**：

1. **L1 止血修复** —— 纯改 bug，零架构风险，**预计砍掉 70% 的等待**。
2. **L2 本地数据通** —— 启用现有未使用的 Dexie 做读缓存，切页/首屏从「等网络」变成「等本地」，这是唯一能把「浏览」做到无感的方案。
3. **L3 首屏拆包** —— 低风险，首屏 3~5 秒 → 1.5 秒左右。
4. **L4 乐观更新** —— 让「做单/编辑/删除」按下即生效，无需等云端回包。

> 我的建议：**L1 + L3 一次做完（风险极低，收益立刻可见）；L2 单独开一版做完再做验收；L4 跟 L2 一起**
> （因为本地通了之后，乐观更新才有可靠的数据源可回滚）。

## 二、顺手查出一棵雷（建议立刻修，与优化无关但影响"优化效果"）

**`public/sw.js:8` 里版本号被写死了：**

```js
const BUILD_VERSION = '2.22.0';   // ← 不是 package.json 的 2.2.2
```

而 `scripts/inject-sw-version.mjs` 的机制是「把 dist/sw.js 里的 `__BUILD_VERSION__` 占位符替换成版本号」，文件里已经有 `scripts/inject-sw-version.mjs:31` 的「未发现占位符就跳过」保护 → **注入从某一版起就永久失效了**。

线上实测 `curl https://bailihongxi.github.io/wholesale-erp/sw.js` 返回的仍是 `BUILD_VERSION = '2.22.0'`。

**后果**：
- 浏览器判断「SW 有没有更新」只比对 sw.js 自身内容 → 内容恒定 → **SW 永不更新**；
- 缓存名永远是 `erp-2.22.0`，`activate` 里「删掉非当前版本缓存」这句永远不执行 → **缓存只增不减**；
- 每次发版以为更新了 SW，实际上没更新。

**修法（一行）**：把 `public/sw.js` 改回占位符 `__BUILD_VERSION__`，让注入脚本重新生效。
**风险**：几乎为零，但**必须在下一次部署时一起发**，否则用户浏览器里那个"永不更新的 SW"会把新代码挡住。

## 三、方案清单（按风险递增，每一档都能独立上线和独立回退）

### L1 · 止血修复 —— 「把已经做错的地方改对」

> 全部是**改 bug**，不改架构、不改表结构、不加新依赖。风险最低，收益最大。

| # | 改动 | 位置 | 预期效果 | 风险 |
|---|---|---|---|---|
| L1-1 | **应收/应付改内存分组**：先一次取回 `payments`，在内存里按 `refOrderId` 分组算，不再逐单查 | `stores/finance.ts:22,50` | 老板工作台 **50 秒 → 300 毫秒** | 极低 |
| L1-2 | **入库/出库明细计数改 `anyOf` 一次取回** | `InboundView.vue:208`、`OutboundView.vue:207` | 50 请求 → 1 请求 | 极低 |
| L1-3 | **商品档案页改服务端分页**：现有 `productStore.listPage()` 已经实现好了，页面却在用 `toArray()` 整表拉 | `ProductListView.vue:378-389` | 14 请求 → 2 请求 | 低 |
| L1-4 | **库存批量更新改 `bulkUpdate` / `bulkAdd`**（数据层已有实现，没用上） | `purchase.ts:170-177`、`sales.ts:192-197` | 80 请求 → 1~2 请求 | 低 |
| L1-5 | **看板/报表类 `useReloadOnActivate` 加节流**（5 秒内且无写操作就复用上次结果） | `BossHomeView.vue:146`、`BossReportsView.vue:254`、`LedgerView.vue:486` 等 | 切页不再重跑首屏 | 低 |
| L1-6 | **批量改价改 `bulkUpdate`** | `ProductListView.vue:673` | 50 次写 → 1 次写 | 低 |
| L1-7 | **`toArray()` 返回副本后再 `.sort()`**：现在原地排序会污染共享缓存，后续调用方拿到被改过序的数组 | `ProductListView.vue:383` | 消除隐患 | 极低 |
| L1-8 | **删单时 `quoteOrders` 用窄字段查**（只要 id/status/关联字段，不要全字段） | `utils/quoteLink.ts:47` | 删单少 1 次全表扫 | 极低 |
| L1-9 | **sw.js 版本号占位符修复** | `public/sw.js:8` | 缓存命名空间恢复正常 | 极低 |

**合计**：约 **8~10 个改动点，2~3 个人日**。

### L2 · 本地数据通 —— 「让读操作不等网络」

> 核心：**启用现有但未使用的 Dexie**，把云端数据在本地留一份，做成 `stale-while-revalidate`（先用本地秒开，再后台静默同步）。
>
> 这其实是把系统**还原到最初设计意图**——`dexie` 在 package.json 里躺着，但 `src/db/` 里 0 处使用。

**做法**：

1. 在 `src/db/` 加一层本地库（`erp_local`，IndexedDB），镜像 9 张 `CACHED_TABLES`。
2. 读路径改成：**本地命中 → 立即返回（0ms）→ 后台比对云端 → 有差异就更新本地并刷新视图**。
3. 写路径：**先写本地 + UI 即时反馈 → 同步推云端 → 失败自动回滚本地并提示**。
4. 启动时做一次「本地 ↔ 云端」校准，用 `updatedAt` 比对，避免单向覆盖。

| 维度 | 现状 | 优化后 |
|---|---|---|
| 切回列表页 | 1~3 秒（重拉） | **< 50ms**（本地读） |
| 打开商品档案 | 14 请求 / 数秒 | **0 请求待渲染**，后台同步 |
| 首屏可用时间 | 3~5 秒 | **1.5 秒左右** |
| 弱网/断网 | 基本不可用 | 仍能浏览已加载的数据 |

**风险（必须正视）**：

| 风险 | 缓解措施 |
|---|---|
| 读到过期数据（用户以为改了，其实没同步） | 列表数据一律带「同步时间」角标；5 秒内静默刷新；写操作强制立刻同步云端 |
| 本地缓存被写坏 / 脏数据 | 启动校验 `updatedAt`；提供「设置 → 清空本地缓存」一键重建 |
| 双向同步冲突 | 首版只做**单向兜底**：本地写 = 立即推云端成功后才落本地；不做离线编辑队列 |
| 存储超限（Safari 无痕会抛异常） | 全部 try/catch，失败自动降级回现有纯云端模式 |

**工期**：约 8~12 人日。
**回退**：加一个开关（内存开关即可），关闭即退回现在的行为，不需要卸载代码。

---

### L3 · 首屏拆包 —— 「把 496KB 拆掉」

**做法**：`vite.config.ts` 加 `build.rollupOptions.output.manualChunks`，把 `vue / pinia / @supabase / vant / 业务视图` 拆成多个 chunk。

| 维度 | 现状 | 优化后 |
|---|---|---|
| 主包 | 496KB 单文件 | 核心约 200KB，其余按需并行加载 |
| 二次访问缓存命中 | 低（一个文件变了全包失效） | 高（库文件稳定，长期缓存） |
| 手机 4G 首屏 | 3~5 秒 | **1.5 秒左右** |

**风险**：**极低**——纯构建配置，不改任何业务代码，构建失败直接回退。

**顺带**：给 Supabase 域名加 `<link rel="preconnect">`，省掉 DNS+TLS 往返。

---

### L4 · 乐观更新 —— 「做单不用等云端回包」

**做法**：抽一个 `useOptimistic()` composable，统一处理「本地立即生效 → 后台确认 → 失败回滚 + 提示」。

| 操作 | 现状等待 | 优化后 |
|---|---|---|
| 点「保存」 | 等 4+N 个请求完成 | **按下即关闭弹窗**，右上角显示同步状态 |
| 点「删除」 | 等 5~7 次串行 | **列表行立即消失**，失败再弹回 |
| 点「确认」 | 等云端回包 | **状态立即翻转** |

**风险**：中——如果不做回滚会「数据看起来没了」。**必须和 L2 一起做**，因为 L2 提供了可靠的可回滚数据源。

**工期**：约 5~8 人日（如果 L2 先做完，边际成本会低很多）。

### 4.3 为什么不建议动架构

- 现有 Supabase 单租户方案对你的团队规模是**合理选择**，改成自建后端等于推翻全部权限、缓存、同步逻辑；
- 手机端体验瓶颈**不在服务端**，而在「请求次数」和「本地缓存」，这两件事 L1+L2 就能解决；
- 换成国内节点只能省一次 RTT（约 100~200ms），**治不了 N+1 和 80 次写请求**。

## 五、可回退保障（你最关心的部分）

我会按下面这套规矩做，**不会出现"改完到处是坑"**：

| 保障措施 | 具体做法 |
|---|---|
| **数据库零变更** | 全程不改任何表结构、不加列、不加索引、不动 RLS。出问题就是纯前端问题 |
| **单改动单 commit** | 每个改动点一个独立 commit + 独立 tag，坏了一格拆一格，不用全盘回滚 |
| **灰度验证** | 先只用「老板 13000000000」这个账号跑一遍全链路，老板确认没问题再铺开 |
| **降级开关** | L2 加一个 `OFFLINE_CACHE` 开关（默认开），一键退回现行纯云端模式 |
| **一键清缓存** | 设置页加「清空本地缓存并重建」，万一数据异常，点一下回到干净状态 |
| **测试底线** | 现有 68 个测试文件全部保留，每改一处先补/跑相关测试；`npm run build` 必须 0 错误 |
| **线上可复验** | 沿用现有流程：构建 → 推 main → 打 tag → 部署 gh-pages → 线上实机复验 |
| **SW 缓存问题** | 修复 `sw.js` 版本号后，**必须等用户浏览器更新 SW 才生效**，这是唯一需要"等"的地方 |
