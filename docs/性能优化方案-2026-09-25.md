## 二、⚠️ 两处新回归 —— 建议优先处理

这两处是本次 V2.1-2.23 提交带进来的。**它们不修，后面所有优化的效果都会打折扣。**

### R1 · 首屏阻塞：启动链路里被塞进了一次云端往返（P0）

**改动前**（初版认定的"已做对，别动"）：
```ts
// stores/user.ts —— 后台非阻塞校验
function validateSessionInBackground(session): void {
  const run = session.kind === 'dealer' ? db.customers.get(...) : db.users.get(...)
  run.then(row => { if (!row || row.status !== 'active') clearSession() }).catch(() => {})
}
```
原注释写得很明白：**「绝不在启动关键路径上 await —— 否则又会回到『首屏白屏 3 秒』的老问题」**。

**改动后**（`stores/user.ts:91,213`）：
```ts
async function validateSession(session) { /* ... */ await db.users.get(session.id) /* ... */ }
// restoreSession() 里：
await validateSession({ id: session.id, kind: session.kind })   // ← 阻塞
```
而 `restoreSession` 被路由守卫 await：
```ts
// router/index.ts:96
if (!userStore.isLoggedIn) {
  await userStore.restoreSession()      // ← 阻塞首屏导航
}
```
`App.vue` 又补了一道：
```ts
onMounted(async () => { await router.isReady(); appReady.value = true })   // ← 等导航就绪才渲染
```

**完整链路**：
```
打开页面 → await router.isReady()
        → 守卫 await restoreSession()
        → await validateSession()  ✈️ 云端往返，串行等待
        → appReady = true → 才渲染 AppLayout
```

**影响**：
- **每一次硬刷新**（不是每次切页，切页有 `isLoggedIn` 短路，不受影响）都要等这趟云端；
- Supabase 新加坡实测 RTT **~230 ms**，手机信号差时 1~3 秒；
- 用户看到的是「一直转圈」——正是原注释警告的那个回归。

**修法（≈10 行，纯改回）**：把 `await validateSession()` 改回后台不阻塞版本。
注意：如果担心"先闪系统再跳登录"，正确做法是**保留后台校验**，只是别让它挡住渲染——
先渲染，校验发现账号失效再 `clearSession()` + 跳登录，视觉上仍然是连续的。

**风险**：极低。是**改回已验证过的旧行为**。

### R2 · 列表切回：砍掉了 30 秒本地缓存，换来"没有骨架屏"（P1）

**改动前**：`useServerPager` 里有 `CACHE_DURATION = 30 * 1000` 的 sessionStorage 列表缓存，切回 30 秒内 **0 请求、秒开**。

**改动后**：缓存函数（`getCache`/`setCache`/`CACHE_PREFIX`）被**整段删除**，改为：
```ts
// useServerPager.ts
async function load(silent = false) {
  if (!silent) loading.value = true       // silent=true 时不显示骨架屏
  try { paged.value = (await opts.loader(...)).rows } finally { loading.value = false }
}
...
useReloadOnActivate(() => { void load(true) })   // 切回：静默
```
同时顶部注释改成了：「数据直接从服务端拉，**不做本地缓存，避免编辑/删除后列表数据不同步**」。

**这里有个逻辑问题需要你判断**：

> 「不做本地缓存」是为了避免数据不同步 —— 但这个目的**根本不需要靠删缓存来实现**。
> 现在的实现是：切回时**照发请求**（数据照样拉最新的），只是**不显示骨架屏**。
> 也就是说：数据同步问题没变，本地秒开也没了，只剩「界面不动」这一个效果。

对比三种做法：

| 做法 | 切回时数据是否最新 | 切回时是否等网络 | 是否显示骨架屏 | 体感 |
|---|---|---|---|---|
| **改动前**（30 秒缓存） | ❌ 30 秒内可能是旧数据 | **否（0 请求）** | 否 | ✅ 秒开 |
| **改动后**（静默刷新） | ✅ 总是最新 | **是（1 次请求）** | 否 | ⚠️ 界面完全不动，可能被当成卡死 |
| **建议做法**（快照 + 静默刷新） | ✅ 总是最新 | 否（先渲染快照） | 否 | ✅ 既秒开又最新 |

**建议做法**就是：保留上一份列表数据，切回时**先把它渲染出来**（立即），
同时**后台静默拉最新**，拉完替换。这样：
- 用户看到的是旧列表 → 立刻有内容，不是白屏；
- 网络回来后自动变成最新，**数据同步问题不存在**；
- 比"删掉缓存但照样等网络"快，**比"只缓存 30 秒"更准确**。

实现方式也简单：`paged` 本来就是 keep-alive 组件里的 ref，切回时它**根本没被清空**，
所以只要把 `load(true)` 里的一句「复用上次的 rows」加上即可，不需要 sessionStorage。

**为什么这属于"优化"而不是"口味问题"**：
切回一个列表页要等一次完整的 Supabase 查询（列表页通常几百毫秒到数秒），
期间界面零反馈。原来至少 30 秒内是秒开的。

**风险**：低。这个改动是**在现有"静默"基础上加回一串旧数据**，不影响任何写操作。

## 三、两项澄清（不是性能问题，但要告诉你）

### 3.1 经销商「隐藏库存」只省渲染，不省流量

`ProductPicker.vue` 的新 `hide-stock` prop 只做了两件事：
```vue
<th v-if="!hideStock">可用库存</th>
<template v-if="!hideStock"><span>{{ p.stock }}</span><span v-if="无货…">无货</span></template>
```

**`p.stock` 依然从云端拉回来了**，只是不渲染。
→ 对经销商来说：**请求数、响应体积、加载耗时一点没变**，只是界面清爽了。

如果你要的是"经销商真的不用下载库存数据"，那需要另做：
选商品时走一条**不查 stock 的轻量查询**（`ProductPicker` 加 `lean` 模式）。
做不做都行，取决于是否在意经销商端那点流量 —— 但**别把它当成性能优化**。

### 3.2 红色印章只在手机端卡片，桌面端表格没有

```vue
<!-- QuotesView.vue:35 —— 在 v-else-if="isMobile" 的卡片分支里 -->
<div v-if="o.status === 'converted'" class="stamp-stamp">已转销售单</div>
<!-- PurchaseQuotesView.vue:35 同理 -->
```
桌面端 `<table>` 分支**没有加印章**。你截图里看到的应该都是手机端。
如果要桌面端也加，说一声（表格里建议用 `.op-cell` 旁边一个小图标或状态列染色，
绝对定位的印章在窄表格里容易重叠）。

### L2 · 本地数据通 —— 「让读操作不等网络」（8~12 人日）

启用 Dexie（依赖已装、`src/db/` 里 0 处 `new Dexie`，纯云端直连）：

| 子项 | 说明 |
|---|---|
| 读取走本地 | 列表/详情首读 IndexedDB（~10ms），后台同步云端 |
| 写操作双写 | 云端成功后再落本地，失败回滚 |
| 失效策略 | 写操作 invalidate 对应表；切页静默刷新兜底 |
| 降级开关 | 设置页加「清空本地缓存」；数据异常自动回退纯云端 |

**这是唯一能让「查询/编辑/删除/切换页面」做到无感的方案**，风险集中在数据一致性。
建议只在 L1 上线跑几天、体感确认后再开。

### L3 · 首屏拆包（1 人日）

`vite.config.ts` 加 `manualChunks`：

| 拆出 | 预估体积 |  benefits |
|---|---|---|
| `supabase` SDK | ~120KB | 不阻塞首屏渲染 |
| `vant` | ~60KB | 同上 |
| 路由级懒加载 | 各页面 | 首屏只下载当前页 |

**收益**：首屏 3~5 秒 → **1.5 秒左右**，且完全不影响业务逻辑。
**收益/风险比最高的一档，强烈建议和 L1 一起做。**

---

### L4 · 乐观更新 —— 「做单不用等云端回包」（5~8 人日）

保存/删除/确认**点击即生效**，云端回包后再校正（失败则回滚并提示）。

**建议与 L2 捆绑**：乐观更新的回滚需要一个可靠的本地数据源，
单独做 L4 在数据不同步时回滚会"滚错"，反而制造混乱。
