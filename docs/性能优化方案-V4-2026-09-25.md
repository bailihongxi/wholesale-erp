## 第三章　问题定性：先说清楚"乱跳转"这件事

你对 V2.1-2.23 的反馈是「登录后不直接进工作台，先跳工作台再跳回登录页 / 跳回上次退出界面」。这个现象是真的，但**V2.1-2.23 改的是症状，不是病因**。

**病因**（一行代码）：

```ts
// src/db/cloudDb.ts:202
const { data, error } = await this.client.from(this.name).select('*').eq('id', id).single()
if (error) return undefined      // ← 网络异常被吞掉，返回 undefined
```

```ts
// src/stores/user.ts:97
if (!row || row.status !== 'active') { clearSession(); currentUser.value = null }
//      ↑ undefined 被当成"账号不存在/已停用" → 踢下线
```

**表现**：
- 旧代码（后台不 await）：`currentUser` 先被设上、几百毫秒后又被清空 → **先渲染出工作台、然后突然跳回登录页**（你看到的现象）；
- V2.1-2.23 改成 await：同样的判定一行没改 → **误踢照旧**，只是从"闪一下"变成"白屏等一轮云端往返"（约 230ms × N）。

**V2.1-2.23 没覆盖到的三条**：
1. 登录成功后的跳转不走校验 —— `LoginView.vue:137` 的 push 命中守卫的 `isLoggedIn` 短路，`restoreSession()` 根本不执行；
2. 误踢的判定条件没改（`!row` 还在）；
3. `App.vue` 新增的 `await router.isReady()` 门控没解决任何问题，只是把白屏从"路由守卫"挪到"App 根节点"。

**顺带排除的干扰项**：Service Worker 不是元凶（`sw.js` 未写 `skipWaiting`/`clients.claim`，不会中途刷页面）；登出后有 4 处显式调用，之后靠下一次导航被守卫送回 `/login`。

| 项 | 内容 |
|---|---|

### 第 2 档：**L1 止血**（消除"明显在等"的体感）

| 项 | 内容 |
|---|---|
| 工期 | ~2 人日 |
| 内容 | ① 老板工作台聚合请求改并行 + 部分改服务端聚合视图；② 应收/应付明细批量取，消除 N+1 串行；③ 商品档案列表列裁剪（6281 行只取列表需要的字段）；④ 入库单明细 80 次写改批量；⑤ 批量改价 50 次串行改批量；⑥ 库存/金额相关的乐观更新**只做纯展示层**（Tab、展开、筛选回显），不做金额与库存 |
| 优点 | 实测 500 单场景 502 请求 ≈ 100 秒 → 预计降到 20 秒以内；用户"点了没反应"的等待感大幅下降 |
| 缺点 | 改动面涉及财务与库存，必须逐个页面实机验证；部分聚合需要新建 SQL 视图或改表（本方案尽量不建新表，优先在请求层合并） |
| 回退 | 一档一 commit 一 tag；每完成一页灰度一页 |

### 第 3 档：**L3 首屏拆包**

| 项 | 内容 |
|---|---|
| 工期 | 1 人日 |
| 内容 | `vite.config.ts` 配 `manualChunks`，把 Vant、ECharts、图表库、路由级视图拆出去；主包从 508KB 压到 ~250KB 量级 |
| 优点 | 首屏必下的代码减半，手机端（4G）体感最明显；改动只落在构建配置，逻辑零改动；77 个 chunk 本来就已经按路由切好了，收拢即可 |
| 缺点 | 首屏可能出现一次额外的 chunk 请求（约 20~80ms），需要配 `preload` 抵消；极端情况可能出现"加载中"闪动 |
| 回退 | 删掉 `manualChunks` 重新构建即可，纯配置级回退 |

### 第 4 档：**L2 本地数据通（Dexie 双写）**

| 项 | 内容 |
|---|---|
| 工期 | **8~12 人日** |
| 内容 | 把 `cloudDb.ts` 那 478 行里的 15 个方法重写为本地 Dexie 优先 + 云端同步，加 schemaVersion 校验与降级开关 |
| 优点 | 理论上限：打开页面几乎瞬时，断网可用 |
| 缺点 | **风险最高的一个**：本地 Dexie 在云端模式下目前是空壳（`db = USE_CLOUD ? cloudDb : _localDb`），启用等于重写一层数据访问；本地与云端双写一致性没有现成校验；出问题可能 silently 产生"本地数据覆盖了云端正确数据"的账目事故 |
| 回退 | 保留降级开关，一键回到纯云端；加"清空本地缓存"入口 |
| 我的建议 | **本期先不排**。当前瓶颈是"请求数与串行"，不是"本地读写速度"，第 2 档做完 70% 的等待感就没了 |

### 第 5 档：**L4 乐观更新**

| 项 | 内容 |
|---|---|
| 工期 | 2~3 人日（已从 V3 的 5~8 砍半） |
| 内容 | 只对纯展示操作立即回显：Tab 切换、行展开、筛选条件回显、分页跳转 |
| 优点 | 用户点下去"立刻有反应"，心理等待感进一步下降 |
| 缺点 | **金额与库存相关一律不做**——你是"款到发货 + 严格全款"，乐观更新回滚失败就是账目事故 |
| 回退 | 逐页面回退 |

### 不做的事（明确排除）

自建后端 / 开 RLS / SSR 服务端渲染 / 换 CDN。理由：RLS 与 Supabase 直连模式冲突；SSR 与纯静态托管（GitHub Pages）不兼容；换 CDN 对新加坡节点的数据往返没有实质帮助。
