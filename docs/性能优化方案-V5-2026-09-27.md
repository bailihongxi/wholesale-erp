# 家电批发 ERP · 深度提速方案 V5

> 日期：2026-09-27　｜　适用版本：V2.2-1.3 起　｜　状态：**待老板拍板开工**
> 目标：把「采购管理 / 采购单列表 / 采购单明细」以及全站其它列表与明细的加载时间从
> 现状 3~6 秒压到 **1 秒级**，且不牺牲任何现有功能与数据正确性。

---

## 一、结论先行：耗时不是「数据多」，而是「往返次数多 + 字段拉太宽」

三件事在拖慢系统，按影响从大到小：

| # | 根因 | 位置 | 现状 | 影响 |
|---|---|---|---|---|
| 1 | **详情页是"串行链"**：6 段 `await` 一个接一个，等于排队 6 次网络往返 | `PurchaseOrderDetailView.vue:435-466`、`SaleOrderDetailView.vue:427-450` 等 | 6 次串行 = 6 × 单次往返 | 单次往返 0.3~2 秒时就是 **2~6 秒** |
| 2 | **商品缓存整表、全字段拉取**：`db.products.toArray()` 把 6286 行 × 全部字段拉下来 | `useProductCache.ts:31` | 实测全表全字段 ≈ **1.4 MB** | 弱网下 **3~6 秒**，且期间商品名显示为「商品#123」 |
| 3 | **财务报表双重 N+1** | `finance.ts:227/229`、`263/265` | 每张销售单查一次明细，**每条明细**再查一次商品 | 200 单 × 5 行 ≈ **1200 次请求** |

> 反直觉但重要：**采购单列表本身已经不算慢**（服务端分页，1~2 个请求）。
> 你感受到的 3~6 秒，主要是「单次往返本身就要 1~3 秒」× 串行的请求数。

---

## 二、实测证据（2026-09-27 本机直连云端实测）

### 2.1 单次请求往返本身就很贵 —— 这是决定性的数字

| 查询 | 实测耗时 |
|---|---|
| `users` 取 10 行（连接已热） | 2.37 / 2.38 / 2.67 / 3.25 / 3.88 秒（5 次） |
| `payments` 过滤（0 行） | 2.07 秒 |
| `stockRecords` 过滤（0 行） | 1.90 秒 |

**结论**：往返次数 = 页面耗时。**能并行的绝不许串行**，能少一次就少一次。

### 2.2 全字段 vs 窄字段（商品 1000 行）

| 取法 | 传输量 | 相对全字段 |
|---|---|---|
| `select=*`（现状） | 226 KB | — |
| `select=id,brand,model,unit,category` | 95 KB | **-58%** |
| `select=id,brand,model` | 59 KB | **-74%** |

6286 行整表：全字段约 **1.4 MB**，窄字段约 **0.37 MB**。

### 2.3 各页面现状请求数（代码取证）

| 页面 / 动作 | 请求数 | 是否串行 | 判断 |
|---|---|---|---|
| 采购单列表 | 2（供应商 + 分页查询） | 串行 | 已较优，可再并 |
| **采购单明细** | **6**（单据 / 明细 / 供应商 / 付款 / 用户表 / 入库流水） | **全串行** | ❌ 主要问题 |
| 销售单明细 | 6（同上结构） | 全串行 | ❌ 同一问题 |
| 入库验货 / 出库拣货 | 5 | **已并行**（C 档优化过） | ✅ 范本 |
| 商品档案列表 | 2~3（服务端分页 + 库存批量） | 部分并行 | ✅ 较好 |
| 盘点 / 调拨 / 退换货 | 各 3~4 | 部分并行 | 🟡 可再收 |
| 老板工作台 | 2 轮 Promise.all + 商品窄扫 | 已分两轮 | 🟡 可再收 |
| **经营报表（毛利 / 月趋势）** | **1 + 每单 1 + 每行 1** | 全串行 | ❌ N+1 |
| 首屏（启动） | 系统设置 1 + 品牌 1 + 管理员初始化 1 + 登录校验 | 部分并行 | 🟡 可合并 |

## 三、优化项总表（按收益排序，可直接照做）

### 第 1 期 · 立即见效（预计 1.5~2 人日，改动集中在「取数」，不动业务逻辑）

| 编号 | 优化项 | 改哪里 | 怎么改 | 预期收益 | 风险 |
|---|---|---|---|---|---|
| **P0-1** | 详情页并行化 | 采购/销售/报价/调拨/盘点/退换货 等所有 `loadOrder()` | 把互不依赖的查询放进一个 `Promise.all`（照抄入库验货页 `InboundDetailView.vue:290-301` 的现成写法） | 采购/销售明细 **6 次串行 → 1 轮**，2~6s → 0.5~1s | 低（不改语义，只改时序） |
| **P0-2** | 商品缓存瘦身 + 按需批量 | `composables/useProductCache.ts` | ① 改用已有 `scanNarrow('id,brand,model,unit,category')`；② 页面改为「只取本页出现的商品 id」批量补（`where('id').anyOf(ids)`） | 1.4MB → 0.37MB；明细页商品名**即时显示**，不再先闪「商品#123」 | 中（需确认没有别处依赖被裁掉的字段） |
| **P0-3** | 财务报表去掉双重 N+1 | `stores/finance.ts:225-234`、`258-268` | 照抄已修好的 `stores/dashboard.ts:106-112/135` 写法：明细一次 `saleOrderItems.toArray()` 内存分组 + `products.bulkGet(ids)` | 1200 次请求 → **3 次** | 低（有现成范本） |
| **P0-4** | 启动期请求合并 | `main.ts` / `App.vue` / 登录流程 | 已完成的 systemSettings 3→1 之后，再把品牌、管理员初始化、登录校验并成一轮 `Promise.all` | 首屏再省 2~3 个串行往返 | 中（登录链路敏感，需真机复验） |
| **P0-5** | 详情页商品名不再等缓存 | 各详情页 `nameOf/unitOf` | 优先用「明细里已带的商品信息」，缺失才回查（配合 P0-2） | 明细首屏就有名字 | 低 |

## 五、怎么验收（不许"感觉快了"，要用数字）

1. **请求数**：浏览器 Network 面板，从点进页面到内容渲染完成的 REST 请求条数
   - 采购单列表 ≤ 2、采购单明细 ≤ 2（现状 6）
2. **时间**：同一台手机、同一网络，改造前后各测 3 次取中位数
   - 目标：列表 ≤ 1.0s、明细 ≤ 1.2s
3. **回归**：受影响测试文件全绿 + `npm run build` 0 错 + 电脑端与手机端各走一遍进货→入库→销售→收款主流程
4. **数据正确性**：改造后核对一次库存与应收应付金额，与改造前一致

## 六、风险与边界

- **不改**：任何业务规则、金额算法、库存增减逻辑、单据状态机。
- **只改**：取数的顺序、范围（字段/行数）与缓存策略。
- **可回滚**：每期单独提交 + 单独打 tag，出问题按基线标签回退。
- 上线节奏仍按惯例：**先电脑端验证 → 再推部署 → 手机端复验**。
