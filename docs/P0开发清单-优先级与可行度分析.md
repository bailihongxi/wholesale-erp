## 二、逐项正确分析

### 1. B1 经销商端产品目录+自助下单
- **状态**：PRD 已就绪，约 70% 骨架代码已存在（dealer 角色、批发价目录、convertToSale 引擎、QuotesView 改造点均已定位）。
- **可行度：高**。核心改造是 `QuotesView.vue` 经销商分支 + 路由/菜单权限 + Realtime 确认回传，无数据架构冲突（复用 `customerId` 过滤，不新增字段）。
- **定位**：这是"经销商渠道"的**入口**。建议作为整个 P0 的第一枪。
- **风险**：唯一坑是 `homeRouteForRole('dealer')` 现指向未建的 `/dealer/catalog` 会导致登录死循环，PRD 已列为 V2.1-1 必改项。

### 2. F4 客户/供应商对账单（合并 S9/P9）
- **关键发现：F4 = S9 + P9**，分建会造成两套相近页面、双倍维护 → **只做 F4**。
- **可行度：高**。`finance.ts` 已能算出每个客户/供应商的应收/应付余额、已收/已付、未结清单据列表。**缺的只是一个"对账单视图"**：按客户/供应商筛选 + 时间区间 + 期初/本期发生/期末余额排版 + 打印。
- **明确边界（决策③）**：F4 **不接 dealer 分支**，经销商对账走电话/微信，不开放自助查看。
- **与 B1 关系**：经销商本质就是 `customers` 一行，F4 的客户对账数据天然含经销商，但**界面上对经销商隐藏**即可，无需为 B1 特别改造 F4。

### 3. F1 发票台账（决策④：关联订单）
- **定义升级**：老板要求**关联订单号 + 选单带出金额 + 误差可查**（防"多货只开一张票"导致后续查询混乱）。
- **可行度：最高**。本质仍是一张发票登记表，但首版即带：
  - 字段：`发票号 / 开票方(客户或供应商) / 订单号(可空，可选单带出) / 金额 / 税额 / 价税合计 / 开票日期 / 发票类型(进/销) / 备注`。
  - **选单带出**：新建发票时选「销售单/采购单」→ 自动带出该单金额、往来方；允许手动调整（留误差空间）。
  - **首版单向查询（发票→订单）**：按「发票号」反查"本发票关联了哪些单"，解决"多行货只开一张票也好查"。**反向（订单→发票：从订单查"开了哪些发票"）首版不做，留待后续版本**。
- **工作量：S~M**（比纯登记略重，因为多了选单关联与单向查询）。
- **价值**：批发业态税务合规刚需，风险最低。

### 4. S10 销售订单批量操作 —— **已取消（决策②）**
- **核对结论**：系统当前**列表页无任何批量操作**，删除按钮**仅存在于单据详情页**（V2.0-28 的 `canDeleteDoc` 闸已在详情页生效）。
- 老板要求"删除必须进入单据后才能删"——**系统现状已完全满足**，且从未提供批量删除。
- → S10 直接从开发计划移除，**无需任何改动**。

### 5. S2 销售 / P3 采购 审批流 —— **已决策：走方案 B「付款放行」+ 预留方案 A「老板审批」接口（A 本次不实现）**

> **决策背景**：老板否决了原"财务确认收款/可付款才能出入库"（每单要 finance 角色点一下，运营重、财务未必实时在线），也否决了额外多一步人工审批，最终定为：
> - **S2/S3 实装方案 B**——零新字段，直接复用订单已有的 `receiveStatus`(销售)/`payStatus`(采购) 做"款到发货"硬闸；
> - **同时把方案 A 的"老板审批"接口预留好**：类型与云端表加 `approvedBy/approvedAt` 可空字段 + 一个休眠的审批闸 + 系统设置开关（默认 false）。**本次不实现审批 UI**，日后启用只需"开开关 + 加审批按钮"两步，无数据库迁移、无逻辑重构。

**核心约束（不变）**：审批人复用现有角色，**不新增"主管/审批人"角色**（与前几轮"权限系统零改造"一致）；销售/采购共用一套逻辑、两处挂。

下面三方案按"改动量从大到小"排列，供回溯参考；**方案 B 为已选定落地项，方案 A 的接口按"预留设计"处理，方案 C 仅作备选**：

#### 方案 A —— 老板单级审批（硬闸）🔧 接口预留（本次不实现 UI）
- **机制**：订单加 `approvedBy?` + `approvedAt?` 两可选字段（向后兼容老单）；详情页 `boss` 及 ≥boss 角色可见「审批通过」按钮，点击写字段 + 审计（`AUDIT_ACTIONS.SALE_APPROVE` / `PURCHASE_APPROVE`）；列表/详情显示「已审批✅/未审批」徽标；`outbound()` 与采购入库函数开头加 `if (!order.approvedBy) 拦截`；UI「确认出库/入库」未审批时置灰。
- **改动文件**：`types/index.ts`(两接口各+2可选字段) · `cloudDb`(两表各+2可空列) · `utils/audit.ts`(+2常量) · `sales.ts` `outbound()`(+闸) · `purchase.ts` 入库(+闸) · `SaleOrderDetailView`/`PurchaseOrderDetailView`(+按钮+徽标) · 订单列表(徽标，可选) · 测试。
- **优点**：真审批、权责清晰（仓库不能自己放行）；复用 boss 角色，无需财务在线。
- **建议配套**：系统设置加「订单需审批」总开关（`SYNC_KEYS` 加键即可云端同步），默认**关**，避免影响存量单与个别通融单。
- **工作量：M**（触及核心出入库，需重点测，但范围清晰）。

#### 方案 B —— 付款状态自动放行（零新字段，最贴合"先款后货"）✅ **已选定落地**
- **机制**：**不新增审批点击、不新增字段**，直接复用订单已有的 `receiveStatus`(销售) / `payStatus`(采购)。`outbound()` 检查 `receiveStatus==='received'` 才放行，否则拦截"款未到不发货"；采购入库检查 `payStatus==='paid'`。
  - ⚠️ **严格全款模式（老板 2026-09-23 确认）**：销售仅 `received`、采购仅 `paid` 才放行；`unreceived`／**`partial`（已付定金但未全款）**／`unpaid`／`partial` **一律拦截**——即"必须全款到账才发货"，定金/部分付款不发货。
- **改动文件**：`sales.ts` `outbound()`(+状态闸) · `purchase.ts` 入库(+状态闸) · 详情页提示文案 · 可选系统设置开关 · 测试。
- **优点**：**零新字段、零新角色、改动最小**；且完美对齐你"款未到不发货"的口头规矩——系统替你把这道关做死，仓库想先放也放不了。
- **缺点**：不是"人审批"，是"钱到账自动放行"；若偶有"先发货后补款"的熟人，需靠开关临时放。
- **工作量：S~M**（只动两个函数，不碰类型/表结构）。✅ **本方案为 S2/S3 实装项。**

#### 预留方案 A 的「老板审批」接口（本次不实现，按休眠设计就位）

> 目的：满足老板"日后启用方便"——现在不做审批按钮、不弹审批 UI，但把数据模型、闸、开关全部就位，将来想加只需两步。

- **数据模型就位**：`SaleOrder`/`PurchaseOrder` 类型加 `approvedBy?`/`approvedAt?` 两可空字段；云端 `saleOrders`/`purchaseOrders` 加 `approved_by`/`approved_at` 可空列（**非破坏性，启用时零迁移**）。
- **单一闸门函数** `checkDispatchGate(order, kind)`（新增 composable 或并入 store）：① 先跑 B 的付款闸（生效中）；② 再跑 A 的审批闸 `if (BOSS_APPROVAL_ENABLED && !order.approvedAt) return 拦截` —— 常量/开关为 false 时**永远不触发（休眠）**。
- **系统设置加 `bossApprovalEnabled`（默认 false）**。
- **日后启用只做两件事**：① 开关设为 true；② 单据详情页加「审批通过」按钮调 `approveOrder()` 写 `approvedBy/At` + 审计（`AUDIT_ACTIONS.SALE_APPROVE`/`PURCHASE_APPROVE`）。**无 schema 迁移、无逻辑重构**。
- **本次不做**：不渲染审批按钮、不显示"已审批/未审批"徽标、不改详情页 UI。

#### 方案 C —— 软审批（仅留痕，最轻，不强制）
- **机制**：同方案 A 加 `approvedBy/At` 字段 + 按钮 + 徽标 + 审计，但 **`outbound()`/入库不加闸**——只是记录"谁在何时批过"，不拦截发货。
- **优点**：改动最小、零风险；满足"谁经手的单老板心里有数"的留痕需求。
- **缺点**：不强制，仓库仍可未经审批就出库。
- **工作量：S**。

#### 三方案对比
| | 新字段 | 谁触发放行 | outbound 是否拦截 | 改动量 | 状态 |
|---|---|---|---|---|---|
| **A 老板审批** | approvedBy/At | boss 点「审批通过」 | ✅ 拦截 | M | 🔧 **接口预留**（字段+休眠闸+开关就位，本次不实现 UI） |
| **B 付款放行** | 无 | 自动（依收款状态） | ✅ 拦截 | S~M | ✅ **已选定落地** |
| **C 软审批** | approvedBy/At | 不拦（仅留痕） | ❌ 不拦 | S | 备选（未选） |

- **S2 与 P3 共用一套**：销售/采购对称实现，做一套、两处挂。
- **工作量**：A=M / B=S~M / C=S（均远小于原"财务确认"的 L，且语义更顺）。
- **✅ 已决策：S2/S3 = 方案 B 落地 + 方案 A 接口预留（本次不实现审批 UI）**。B 解决"款到发货"真痛点；A 的字段/闸/开关就位但休眠，日后启用零返工。

## 四、互相牵制分析（决策⑤：各功能能否独立成版）

**结论：无硬阻塞，每个功能都可独立开发、独立发版、各自稳定。** 理由逐条：

| 功能 | 改动文件范围 | 是否阻塞他人 | 说明 |
|---|---|---|---|
| **B1** | `QuotesView.vue` + 路由/菜单 + Realtime 订阅 | 否 | 纯加 dealer 分支，不动核心流程 |
| **F4** | 新增对账单页（只读聚合） | 否 | 只读 `finance.ts` 现有聚合，不改写数据 |
| **F1** | 新增发票表 + 页 + 选单关联 | 否 | 新表独立；选单只**读**现有订单表，不改订单 |
| **S2/P3** | `outbound()`/入库函数加 **B 付款闸**（零新字段）；预留 A 的 `approvedBy/At` 字段+休眠闸+系统开关（本次不实现 UI） | **否（但需重点测）** | 改的是核心出入库流程，但**不改动其它功能代码**；B1/F4/F1 都不碰 outbound，互不影响 |

**唯一需你知晓的"软关联"（非阻塞）**：
- S2/P3 上线后，F4 对账单**可顺带显示"财务已确认/未确认"**，但 F4 先发版时不显示该列也完全可用 → 不影响各自稳定。
- S2/P3 是对**全公司出入库行为的全局规则变更**，建议**单独一个版本、充分自测**（尤其"未确认时被拦截"的边界与"开关关闭时放行"的回退），不要和别的功能混在同一版本里，便于出问题时精准回滚。

→ 故**决策⑤成立**：按"每功能一版"的节奏最稳妥，推荐发版顺序见下。
