## 第二章　现状体检（全部实测，附代码位置）

### 2.1 一次网络请求有多贵（成本模型）

数据源 `src/db/cloudDb.ts`。Supabase 新加坡节点，单次往返（RTT）实测 **200~400ms**；单次请求最多回 **1000 行**。

| 写法 | 实际代价 | 证据 |
|---|---|---|
| `db.X.toArray()`（全表） | 命中内存缓存＝**0 请求**；否则 `ceil(行数/1000)` 次（商品 6281 行＝**7 次**） | cloudDb.ts:184-217 |
| `where(f).equals(v).toArray()` | **1 次**，但**不走内存缓存**（CloudQuery 是独立实现） | cloudDb.ts:89-116 |
| `get(id)` 单行查 | **1 次**，且**不走缓存** | cloudDb.ts:231-235 |
| `add / update / delete` | **1 次**，并且会 **invalidate 整张表缓存** | cloudDb.ts:262-323 |
| `bulkPut / bulkAdd / bulkDelete` | **1 次**（一次写 N 行） | cloudDb.ts:276-310 |
| `.map(x => db.X.update(x))` | **N 次**（看起来像批量，其实是 N 个单行请求） | 见 sales.ts:193 |

### 2.2 五大瓶颈（按"疼"的程度排序）

#### 🔴 瓶颈一：单据写入是**逐行写**，不是批量写 —— 这是"点完单据转好几秒"的头号元凶

| 链路 | 现状写法 | 5 行单据的请求数 |
|---|---|---|
| 销售出库 | `sales.ts:193-194` 库存扣减：`stockToUpdate.map(u => db.stock.update(...))` + `locationStock` 同样逐行 | **2N + 5 ≈ 15** |
| 采购入库 | `purchase.ts:171-174` stock 更新 N + 新增 M + locationStock 更新 N + 新增 M | **2N + 2M + 3 ≈ 13** |
| 销售退货 | `returns.ts:94-112` 每行 6 次串行（明细 add + 库位增量 + 总库存查 + 总库存写 + 流水 add） | **6N ≈ 30** |
| 采购退货 | `returns.ts:168-184` 同上 | **6N ≈ 30** |
| 调拨单 | `inventory.ts:365-372` 每行 6 次串行 | **6N ≈ 30** |
| 盘点过账 | `inventory.ts:435-458` 每行 6 次串行 | **6N ≈ 30** |
| 建/改报价单 | `quotes.ts:50 / :108` 明细 `for → await quoteOrderItems.add` | **N ≈ 5** |

> 一张 5 行的退货单＝**30 次串行请求 ≈ 6~12 秒**。这是全系统最慢的单据操作。

#### 🔴 瓶颈二：写一行库存 → 整张库存表缓存作废 → 重拉 6281 行

`stock` 表在 `CACHED_TABLES`（cloudDb.ts:158），但 **每一次 `db.stock.update()` 都会 `invalidate()` 整表**（cloudDb.ts:318-323）。
于是：出库写完 N 行库存 → 下一次任何地方读 `db.stock.toArray()` → **重新拉 6281 行＝7 个请求**。

**这就是"点完出库，页面转好几秒才出来"的真正原因**——不是出库慢，是出库后的刷新在搬 6281 行数据。

#### 🟠 瓶颈三：详情页/工作台的 **串行接力**

| 位置 | 现状 | 请求数 |
|---|---|---|
| `OutboundDetailView.vue:270-328` | 库房查 3 次（还重复）→ 单据 → 明细 → 商品 → 客户 → 流水 → 出库单列表，**7~9 段全程串行** | ≈ 15~20 |
| `InboundDetailView.vue:258-318` | 同上，**9 段串行** | ≈ 15~20 |
| `SalesHomeView.vue:82-91` | 客户 → 待发货 → 订单 → 应收，**4 段串行且互不依赖** | ≈ 5（可省 3 个 RTT） |
| `PurchaseHomeView.vue:80-94` | 同上 | ≈ 5 |
| `WarehouseHomeView.vue:96-112` | 4 路并行 ✅ → 然后又**串行**拉最大的 `stockRecords` | ≈ 7 |
| `FinanceHomeView.vue:139-156` | 5 路并行 ✅，但 **`payments` 同一张表被拉了 3 次** | ≈ 6 |
| `BossHomeView.vue`+`dashboard.ts:76-146` | **12~14 个请求，其中 6 段完全串行**；`payments` 拉 2 次 | ≈ 14 |

**其中最离谱的一处**（`product.ts:270-283`）：老板工作台为了显示"低库存预警 **一个数字**"，扫了 **6281 行商品 + 6281 行库存＝14 个请求**。

#### 🟠 瓶颈四：有现成的服务端分页不用，还在拉整表

| 页面 | 现状 | 应该的样子 | 请求数变化 |
|---|---|---|---|
| **商品档案页** `ProductListView.vue:380` | `db.products.toArray()` 拉全量 6281 行到内存再前端切片 | `product.ts:378` 的 **`listPage()` 已经写好了却没用** | **14 → 1** |
| 库存库位页 `LocationsView.vue:147-157` | `locationStock` 同一张表**被拉两次**，4 段串行 | 合并 + 入缓存 | ≈15 → ≈3 |
| 盘点页 `CountView.vue:229-238` | 5 段串行，每次切回页面**整链重跑** | 并行 + 接缓存 | ≈16 → ≈3 |
| 调拨页 `TransferView.vue:243-258` | 与盘点页完全同构 | 同上 | ≈16 → ≈3 |
| 收支流水 `LedgerView.vue:309-320` | 为了一个"关联单号"下拉，**把 5 张表整表拉回来只取 orderNo** | 窄字段 / 按需 | ≈8 → ≈2 |

另外 26 个页面挂了 `useReloadOnActivate`。机制本身没问题，但**接的函数有贵有贱**：
- 便宜的（单页重拉 1 次）：销售单/采购单/客户/供应商等 8 个服务端分页页 ✅
- **昂贵的（切回一次重跑整条全量链）**：商品档案 7 次、盘点 16 次、调拨 16 次、库位 15 次 ← **"来回切一下就转圈"的来源**

#### 🟡 瓶颈五：首屏一个 498KB 的大文件，配置里零分包

## 第四章　安全红线（每一档都按这套执行）

1. **语义等价替换**：批量写 = 逐行写的数据结果；并行 = 串行的最终结果；`anyOf` = 逐个 `get` 的结果。任何一处不等价就不做，改用别的办法。
2. **失败降级兜底**：所有批量写包 `safeBulk()` —— 批量失败时**自动退回逐行重试**，最差＝现状，绝不比现在更慢/更容易失败。
3. **一档一 commit 一 tag**：`v2.1-2.34-A` … `v2.1-2.34-E`，任何一档出问题只 revert 那一档。
4. **每档硬门槛**（不达标不进下一档）：
   - 单文件 vitest 通过（**`--no-file-parallelism`**）
   - `npm run build`（`vue-tsc -b`）**0 报错**
   - 新增静态测试锁死本档契约（例如"出入库不得再出现逐行 update"）
   - **老板账号实机走通一个完整业务动作**：建单 → 改单 → 转单 → 出库/入库 → 删除 → 切页
   - **电脑端（1280）+ 手机端（390）双端均通过**
5. **每档上线后等你验收**，再开下一档。
