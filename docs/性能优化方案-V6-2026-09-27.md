## 一、加载时间（首屏）

### 现状与实测
- 路由已是懒加载（router 42 处 `import()`，dist 里有 per-view chunk），Vant 已按需摇树——这两块**不用再动**。
- 未拆包基线：主包 508KB / gzip 155KB 单文件；CSS 98.5KB。
- 工作区已有的 manualChunks 拆包（未提交）实测效果：

| chunk | 体积 | 说明 |
|---|---|---|
| supabase-vendor | 227KB | 变化最少，长期缓存命中 |
| index（业务主包） | 167KB | **从 508KB 降下来**，以后每次发版只让它失效 |
| vue-vendor | 113KB | 长期缓存命中 |
| vant-vendor | 23KB | — |

### 建议（按收益排序）
1. **【高收益·低风险】提交工作区的 manualChunks**，补两件事：
   - SW 预缓存列表适配（`inject-sw-version.mjs` 兼容多 chunk，实测 `erp-` 版本注入需复验）；
   - 老版本用户升级路径验证（SW 缓存名必须每版都变——现有铁律不变）。
2. **dexie 从主包拆出**（约 60KB）：只在 `src/db/index.ts` 引用，`manualChunks` 加一条 `'dexie-vendor': ['dexie']` 即可，顺手的事。
3. **【中收益·中风险·可后置】CSS 98.5KB 瘦身**：Vant 样式按需引入（unplugin-vue-components）。预计砍 30~50KB，但动构建链，建议单独一档、充分实机验证后再上。
4. **首屏数据请求**（恢复 C 档后已解决大半）：老板工作台 12~14 请求 → 两轮并发；商品档案首屏 14 请求 → 1 请求。

**预期**：首次冷启动可交互 ~2.5s → ~1.5s；老用户二次进入命中 SW + vendor 缓存 <1s；日常发版后用户只需重新下载 ~167KB 业务包而不是 508KB。

## 二、单据流转（写链路）——「点完出库卡几秒」的根因在这

### 逐行写入（A/A2 档已解决，等恢复）
- 退货单：30 次请求 → 4~6 次；出入库/调拨/盘点明细全部批量化；5 行盘点单 30 请求 → ~6 次。
- 均带 `safeBulk()` 失败降级逐行重试，最差等于现状。

### 缓存失效风暴（B 档已解决，等恢复）
- `stock` 在 CACHED_TABLES 里，**每写一行库存就让 6281 行整表缓存作废**，下一个读缓存的页面重拉 14 请求。这是"出库转好几秒"的真因——不是出库慢，是出库后第一次刷新在搬全表。
- B 档方案：写操作改为**增量 patch 缓存**（只更新被改的那几行），不再整表作废。

### 还没做的（建议作为下一档，暂称 D2 档）
报价单 → 销售单的转换链路（实测 N+12 请求）：
- `quotes.ts:203` 白拉一次全量 products；
- `quotes.ts:226` 明明有单号还回查一次 orderNo；
- `sales.ts:102` 总金额二次 update；
- `sales.ts:134` 重复查 locations；
- `sales.ts:59-61` 逐商品查库存 → 应改 `stockOf(ids)` 批量。

**预期**：转单从 ~3-5s → <1s；出库确认后不再有"卡几秒"感。

## 三、单据显示（读链路）

### 详情页与列表（C 档已解决，等恢复）
- 出入库详情 `loadOrder` 7~9 段串行（15~20 请求）→ 两轮并行；
- `listDocsByRefOrder()`：详情页不再为一张单扫全表流水 + 全表明细；
- 出入库列表 N+1 清零（计数批量 + 两请求并行）。

### 剩余热点（建议后续分两步）
1. **切页重跑风暴**：26 页挂 `useReloadOnActivate`，其中 4 个贵的——盘点 16 请求 / 调拨 16 / 库位 15 / 商品档案 7，**每次切回来都全量重跑**。建议：给这 4 页加「5 分钟 TTL 软刷新」（缓存未过期就直接显示 + 后台静默校新），体感是切页瞬时返回。
2. **CloudQuery 不走内存缓存**：`where/anyOf` 查询绕过 CloudTable 缓存，dashboard/sales 十余处在重复拉全表。建议：对 CACHED_TABLES 的等值查询先查内存再回落网络。
3. **下拉类窄字段推广**：「记一笔」单号下拉已改只拉一列（C 档），同款做法可推广到客户/供应商选择器（现在也是整行整表地拉）。

**预期**：详情页打开 ~2s → <0.8s；页面间切换高频路径基本瞬时。

## 四、数据存储（云端与缓存层）

1. **缓存表清单再校准**：`CACHED_TABLES` 现在 10 张全表缓存。`saleOrders` 0 行缓存了也白缓存（缓存命中判断别只看表名，空表直接跳过可以省一次判断链路）；`stock` 走 B 档增量后才能真正留在这个名单里。
2. **云端索引（免费的高收益）**：Supabase Postgres 侧确认以下索引存在，没有就补上——
   - `stock(productId)`、`stockRecords(refOrderId)`、`stockRecords(type)`、`purchaseOrderItems(purchaseOrderId)`、`saleOrderItems(saleOrderId)`
   - RLS 未开、无权限过滤开销，索引是纯白捡的提速，对 >1000 行的表过滤效果立竿见影。
3. **服务端 count 陷阱延续**：`CloudQuery.count()` 挂 filter 时按过滤结果计数的既定口径不变（9-25 事故教训），新加的批量计数路径要带回归锁。
4. **运营性风险提醒**：Supabase Free 层 7 天不活跃会暂停——现在每天有真实使用，问题不大，但建议老板留意暂停告警邮件。

**预期**：大表过滤查询从几百 ms 降到几十 ms；缓存层从"整表失效"变为"按行 patch"，云端请求总量预计降 50% 以上。
