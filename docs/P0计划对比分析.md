# P0 核心功能开发计划 · 对比分析与可取性评估

> 对比对象：用户提供的 `P0核心功能开发计划.docx`（桌面）
> 对照基准：本系统现状（代码 `src/`）+ 此前 `docs/ERP深度开发可行性研究报告.md`
> 结论先行：**方向可取，但需 4 处修正 + 2 处补齐后再定稿**；原 12 天排期偏乐观，建议各模块加 30%~50% 缓冲。

---

## 一、计划速览（文档内容还原）

计划含 5 个 P0 功能，约 12 天，分两批：

| 序号 | 功能 | 计划开发量 | 优先级 |
|---|---|---|---|
| 1 | 收款单 + 付款单 + 核销 | 3 天 | 第一 |
| 2 | 成本核算（移动加权平均法） | 2 天 | 第二 |
| 3 | 利润分析报表 | 2 天 | 第三 |
| 4 | 库存金额统计 | 1 天 | 第四 |
| 5 | 审批流（基础版） | 4 天 | 第五 |

影响范围：新增 10 个页面、修改 8 个现有页面、新增 5 张表、修改 4 张现有表。
设计亮点是审批流的"老板先一人审、后期招到主管后自动流转"思路，比较务实。

---

## 二、与系统现状核对（关键发现）

### 🔴 发现 1：功能一"收付款 + 核销"大部分已实现，计划会造平行表

`src/stores/finance.ts` 当前已具备：
- **收付款登记** `recordReceipt` / `recordPayment`（第 103–160 行），写入 `payments` 流水表并更新单据收款/付款状态（即核销）；
- **应收 / 应付**余额计算（第 8–64 行）；
- **记一笔**日常收支（第 252–302 行）。

UI 侧已有 `views/finance/ReconcileView.vue`（应收/应付/收付款流水三 Tab）与 `FinanceOpsView.vue`（收付款 + 记一笔合并时间线）。

**冲突点**：计划"数据结构变化"要**新建 `payment_receipts` / `payment_orders` 两张表**，这会**与现有 `payments` 表重复**，导致收付款数据分裂成两套，后续对账永远对不上。
**修正**：不要新建平行表。应**复用现有 `payments` 表与收付款登记逻辑**，把计划里的"独立收款单列表 / 新建页 + 预收预付 + 核销明细"作为**现有能力的 UI 外置与增强**来落地。

### 🔴 发现 2：成本核算的可行性存疑——历史库存变动没有成本字段

逐行核对 `stockRecords` 的写入（`inventory.ts` 调拨、`purchase.ts` 采购入库、`sales.ts` 销售出库、`returns.ts` 退换货）：所有流水只记 `type / productId / quantity / refOrderId / operatorId / createdAt / locationId / batchNo`，**没有单位成本字段**。

移动加权平均成本要求**每一条历史库存变动**都带有成本（入库用进价、出库用当时均价、退换货/调拨/盘点同样要成本）。计划风险表自己也写"历史数据没有成本 → 上线前做一次成本盘点"——但这只解决了**期初库存**的盘点成本，**解决不了历史加权**：
- 上线前的销售出库成本、退货成本、调拨成本全部缺失；
- 若强行从上线日向前追历史成本，需要重建每一笔历史采购进价，工作量巨大且不现实。

**修正（二选一，必须写进计划）**：
- **方案 A（推荐个体户）**：明确"加权成本从上线日起算，历史数据不作追溯重算"；上线前盘点只用于设定**期初库存数量 + 期初单位成本**，此后的出入库按移动加权滚动。历史利润报表只覆盖上线后区间。
- **方案 B**：若确实需要全量历史成本，则必须在"成本核算"前增加一个"历史采购进价回填"子任务（扫描历史采购单补 `stockRecords` 成本），这会让该模块从 2 天变成 5~7 天。

### 🟡 发现 3：利润分析报表与现有"经营报表"重叠

`views/boss/BossReportsView.vue` 已有：销售额、毛利、毛利率、销售毛利趋势（近 6 个月）。
计划的"利润分析报表"（今日/月度概览、利润趋势图、商品/客户利润排行）与之**部分重叠**；差异点仅在于：净利润（扣费用）、商品利润排行、客户利润排行、30 天粒度趋势。

**修正**：在现有经营报表上**扩展**而非新建平行页面，复用现有聚合逻辑，只补齐"扣费用后的净利润 + 商品/客户利润排行"两块。

### 🟡 发现 4：审批流依赖的"主管角色"在权限系统里不存在

`composables/usePermission.ts` 当前角色集合仅为 `['boss', 'purchaser', 'finance']`（外加销售员/仓管员隐含），**没有采购主管 / 销售主管 / 财务主管 / 仓库主管**。
计划假设"员工管理里把主管角色分配给员工，系统自动流转"——前提是员工管理支持**自定义/新增角色**。经核对，角色并非写在员工管理页面的可配置列表里，而是散落在权限判断中。

**修正**：先确认员工管理是否支持新增角色；若不支持，审批流要**连带改造权限系统**（新增角色枚举 + 各页面权限判定），这会让"审批流 4 天"进一步膨胀。建议审批流第一版**只做老板单人审批**（计划本身也这么设计），主管角色作为后续可选扩展，避免首版被权限改造拖死。

### 🟡 发现 5：审批流状态机与现有单据 `status` 字段可能冲突

现有销售/采购单已有 `status`（如 pending/approved/completed，退货、删除、撤回都基于它）。计划新状态机"草稿→待审批→已审批→已完成"是否**重写**现有 status，还是**叠加**一层审批态，计划未说明。不清会导致列表页、详情页、统计全乱。

**修正**：明确"审批态基于现有 status 字段扩展（新增 `submitted`/`rejected` 等枚举值）"，不要另起一套审批字段。

### 🟡 发现 6：库存金额统计与现有"库存金额卡"重叠

首页工作台与库存页已有"库存金额"统计卡（受进价权限 `canSeePurchasePrice` 控制）。计划新建独立"库存金额统计"页（按库房/类别分布 + 饼图/条形图 + 明细列表）属于**增强**而非从零建设。

**修正**：复用现有库存聚合查询，新增"按库房/类别分布图 + 明细列表"即可，不要重复写聚合。

### 🟢 发现 7：计划未提及、但收付款闭环必备的两项

- **信用额度 / 账期**：做了收付款核销却不做账期，核销会退化为"事后记录"而非"事前管控"。建议把"客户信用额度 + 账期预警"并入功能一，否则应收越积越难管。
- **对账单**：核销的终点是客户/供应商对账单。建议在收付款模块一并产出"对账单"，不必单独立项。
- **发票台账**：批发行业税务合规关键，计划完全未提。至少应**预留发票字段/接口**，不必 V1 做全。

## 三、与本研究报告（ERP深度开发可行性研究报告.md）的差异

| 维度 | 用户 P0 计划 | 我的研究报告 P0 |
|---|---|---|
| 主战场 | **财务核算 + 审批**（偏会计正规化） | **运营闭环加固**（毛利预估/换货/安全库存/发票/坏账/对账/审计） |
| 收付款 | 作为独立大功能（3 天） | 拆进"对账单/坏账核销"，未单列独立收付款单 |
| 成本核算 | 明确做（移动加权，2 天） | 放在 P2"会计正规化"，标注"个体户不建议" |
| 利润/库存报表 | 明确做 | 视为"经营报表已有，仅补强" |
| 审批流 | 明确做（4 天） | 放在 P1"业务深化"，未进 P0 |
| 我 P0 的运营项（毛利预估/换货/安全库存/发票/审计） | **完全未含** | 核心 |

**客观评价**：两份文档不矛盾，是**同一系统的两条可选深化路线**——用户选了"先把钱算清 + 加审批闸"，我原建议是"先把运营闭环补牢"。用户路线更贴合"老板最痛的是账算不清、怕员工乱来"，方向合理。需要补齐的是：用户路线**跳过了发票/对账/信用**，而这三者正是"收付款"能落地成"管控"而非"记录"的前提，建议并入。

## 四、可取性结论

**总体：可取，但属于"路线正确、细节需打磨"型，不能直接照原稿开工。**

### 必须修正的 4 处（开工前定稿）
1. **功能一**：复用现有 `payments` 表与收付款登记逻辑，**删掉新建 `payment_receipts`/`payment_orders` 两张平行表**；预收预付 + 核销明细作为增强落地。
2. **功能二（成本核算）**：明确"加权成本从上线日起算、历史不追溯"边界（方案 A），或显式增加"历史进价回填"子任务（方案 B，+3~5 天）。
3. **功能三/四（报表）**：在现有"经营报表 / 库存金额卡"上扩展，不新建平行页面。
4. **功能五（审批流）**：明确基于现有 `status` 字段扩展；首版只做老板单人审批，主管角色作为可选扩展，避免连带改造权限系统。

### 建议并入的 2 项（与功能一打包）
5. 客户/供应商**对账单** + **信用额度/账期预警**（让收付款成为管控）。
6. **发票台账**至少预留字段/接口（税务合规）。

### 工作量重估（更现实）
| 功能 | 原计划 | 修正后建议 |
|---|---|---|
| 收付款+核销（复用现有） | 3 天 | 2 天（外置 UI + 预收预付 + 核销明细） |
| 成本核算 | 2 天 | 3~5 天（含边界澄清/历史回填） |
| 利润报表（扩展现有） | 2 天 | 1.5 天 |
| 库存金额（扩展现有） | 1 天 | 0.5~1 天 |
| 审批流（老板单人版） | 4 天 | 3~4 天 |
| **新增**：对账+信用+发票接口 | 0 | 2~3 天 |
| **合计** | **12 天** | **约 14~20 天** |

## 五、给你的决策建议

1. **能采纳**：5 个功能的**选题和方向**都正确，尤其收付款+审批是老板当前最该解决的问题。
2. **不能直接干**：原稿有 1 个数据架构冲突（平行表）、1 个可行性盲点（历史成本）、3 处与现有功能重叠/冲突，照做会出现"数据分裂 + 历史利润算不准 + 权限改造爆雷"。
3. **推荐动作**：按本文第四节 4 修正 + 2 并入，把排期从 12 天重估到 14~20 天，再进入逐版开发（延续 V2.1 系列节奏，每版守既有铁律：测试只加不删、收尾全量 + build、版本收口 5 处、改菜单跑 nav 权限测试）。

> 注：本文所有核对结论均基于 2026-09-23 本地代码现状（当前产品版本 V2.1-1.2），开工前建议再 grep 一次相关 store 确认未变。
