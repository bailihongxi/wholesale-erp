# 家电批发 ERP 深度开发可行性研究报告

> 编制：2026-09-23　｜　当前版本：V2.0-29（已部署）
> 用途：对照标准 ERP（销售/采购/财务）梳理本项目当前能力，列出**待改进/可借鉴清单**与**详细开发计划**，
> 供老板研究后决定**是否**、**先做哪块**、**做到什么深度**。本报告不改动任何代码。

---

## 一、结论先行（TL;DR）

| 档位 | 含义 | 建议项数 | 总工作量 | 推荐度 |
|---|---|---|---|---|
| **P0 · 流程闭环加固** | 补当前流程明显缺口、不引入新表大类 | 9 项 | 小~中 | ⭐⭐⭐⭐⭐ 强烈建议先做 |
| **P1 · 业务深化** | 引入"管理型"能力（信用/审批/返点/提成/对账单等） | 11 项 | 中~大 | ⭐⭐⭐⭐ 建议在 P0 之后选做 |
| **P2 · 会计正规化** | 凭证/科目/税务/多账户/折旧等 | 7 项 | 大 | ⭐⭐ 个体户自用可不做，留接口 |

**核心判断**：
- 本项目作为「**个体户/小家电批发商自用**」的进销存，已具备**完整业务闭环**（销售→出库→收款→退货、采购→入库→付款→退货、调拨/盘点/退换货、记一笔+经营报表）。
- 与"正规 ERP"的差距**集中在管理深度与会计正规化**，不是"流程没打通"。所以**不必全面追平**，应**按经营痛点选做**。
- 最该先补的是 **P0**：销售订单毛利预估、客户对账单、供应商对账单、安全库存自动补货建议、销售换货、采购请购/比价、采购费用分摊、发票台账、坏账核销——这些**单点改造、单表新增**即可，工作量小但对日常经营立竿见影。
- **P1 里**最值得做的是**信用额度+账期预警**、**多档客户分级定价**、**业务员提成**、**销售返点**——决定能不能"放心赊销、放心分级定价、给业务员算提成"。
- **P2**（凭证/科目/复式记账/增值税申报/固定资产）属会计系统范畴，个体户通常用不上，且会**根本改变数据模型**，建议**只留接口不实现**，或交给外部财务软件对接。

## 三、标准 ERP 参考流程（与本项目对照）

### 3.1 标准销售流程

```
客户档案 → 销售报价 → 销售订单(信用/折扣审批) → 发货通知 → 出库 → 配送 → 签收
   → 开票(销项税) → 应收 → 收款 → 核销
   → (退货/换货) → 红冲 → 库存回流 → 应收调整
   → (月结) → 客户对账单 → 返点/返利核算
```

### 3.2 本项目销售流程

```
客户档案 → 报价单 → 销售订单(无审批、无信用校验) → 出库(分次) → 应收 → 收款 → 核销
   → (仅退货) → 库存回流 → 应收冲减
```

**关键缺失**：信用额度校验、订单审批、开票台账、换货、对账单、返点。

### 3.3 标准采购流程

```
请购单(各部门) → 询价比价 → 采购订单(审批) → 到货预报(ASN) → 来料质检(IQC)
   → 入库 → 开票(进项税) → 应付 → 付款 → 核销
   → (退货/换货) → 红冲 → 库存流出 → 应付调整
   → 供应商评估(交货/质量/价格) → 月度对账
```

### 3.4 本项目采购流程

```
预采询价 → 采购订单(无审批) → 入库(分次/验收备注) → 应付 → 付款 → 核销
   → (仅退货) → 库存流出 → 应付冲减
```

**关键缺失**：请购单、比价表、到货预报、质检单、采购费用分摊、供应商评估、对账单。

### 3.5 标准财务流程

```
凭证(分录) → 总账 → 明细账 → 试算平衡 → 月结 → 报表(资产负债/利润/现金流)
   + 进项/销项税台账 + 发票管理 + 银行对账 + 固定资产 + 折旧 + 费用报销 + 坏账
```

### 3.6 本项目财务流程

```
应收应付(自动从采销生成) + 记一笔(日常收支) + 资金流水 + 经营报表(利润雏形)
```

**关键缺失**：凭证/科目/复式记账、税务台账、发票台账、银行对账、固定资产、坏账。

## 五、推荐改造包（分阶段）

### 5.1 P0 · 流程闭环加固（强烈建议先做 · 9 项）

> 共同特征：**单点改造、单表新增字段/单页新增 Tab**，不动数据模型骨架，1~2 个版本可上线，**对日常经营立竿见影**。

| 包内序号 | 对应清单 | 一句话 | 工作量 |
|---|---|---|---|
| P0-1 | S7 | 销售单开单/改单实时显示预计毛利 | S |
| P0-2 | S8 | 销售退货支持"退货并换货" | M |

## 八、风险与决策点

1. **数据模型演化**：P0 多为加字段/加单表，云端 Supabase 需配套执行迁移 SQL（项目已有 `settingsSql.ts` 自助建表范式，可复用）。**风险低**。
2. **权限蔓延**：审批/信用/坏账等新动作要进 `usePermission` + `audit.action`，**必须同步 nav-permission 测试**。
3. **手机端适配**：所有新 Tab/新页必须遵循现网手机端规范（卡片、`SegmentedTabs`、不写裸 `input`），否则会重蹈 V2.0-21 之前的覆辙。
4. **性能**：对账单/业绩/返点等多表聚合，**不要走 `toArray()` 全量**，要走 `queryPage` + 列裁剪（项目已踩过 N+1 与全量拉取的坑）。
5. **会计正规化（P2）的诱惑**：个体户自用**不需要复式记账**，做了反而让老板看不懂、维护负担倍增；建议**只做"简化版多账户+月结+发票台账"**，真正的总账交给外部财务软件/代账。
6. **Realtime/Auth（D2/D3）是多人协作前提**：若店铺只有老板一人操作，**暂不必做**；一旦有 ≥2 人同时录入，再做。
7. **版本节奏**：每个版本仍建议**改完即本地提交、等命令再部署**（沿用现行约定），避免并发会话覆盖。
