# 家电批发 ERP · 深度流畅度优化方案 V8（系统级治本）

> 日期：2026-09-29　｜　适用版本：V2.2-1.13 之后　｜　状态：**方案待老板拍板（未开工）**
> 目标：V6（列表提速，已上线）+ V7（列表剩余缺口，已搁置）之外，做一次**系统级流畅度治理**，覆盖
> **启动 / 开单 / 库存 / 财务 / 经销商 / 员工** 六大维度，重点消除四类症状：
> **打开慢、卡死、乱跳转（重拉闪屏）、导航来回反复加载**。
> 不改任何业务规则、金额、库存、状态机，纯改「取数范围 / 缓存策略 / 内存上限 / 预热口径」。

## 一、您最关心的四个症状 → 根因 → 对策（先给结论）

| 症状 | 真实根因（已逐行核实） | 对策（治本，非打补丁） |
|---|---|---|
| **打开慢 / 冷启后发沉** | 登录后 `warmUp()` 把商品表 **全字段** `toArray()` 6281 行≈1.4MB 一次拉进内存（`src/db/cloudDb.ts:640-649` + `src/stores/user.ts:200,216,271,292,305`） | **Z2**：warmUp 商品改用窄字段 `scanNarrow`（照搬 `useProductCache` 现成写法）→ 1.4MB→~0.4MB |
| **卡死 / 弱机越用越卡** | `<keep-alive>` **无 `max` 上限**，60+ 路由组件全常驻内存（`src/App.vue:18-20`），含 `StockManageView` 缓存的 6453 行数组 | **Z1**：keep-alive 加 `max`（LRU 淘汰，如 10~12）→ 内存封顶、弱机不再累积卡死 |
| **卡死（仓库作业）** | 调拨/盘点每次进页（`useReloadOnActivate`）全量拉 `listProductLites()`(6281) + `syncLocationStock()`(全 stock+locationStock)，并以**客户端 `:rows` 模式**把全量商品驻内存（`src/views/warehouse/TransferView.vue:200-272`、`CountView.vue:201-274`） | **K2**：改服务端 loader（`pickerPage`，与开单同套）或复用已预热缓存，不再每次进页全量 + 内存驻留 |
| **乱跳转 / 返回闪屏 / 反复加载** | 各首页 `useReloadOnActivate(reload)` 每次返回都**重拉全表** `orders`/`payments`，且跨页**无应用级缓存**（`SalesHomeView.vue:78-95`、`PurchaseHomeView.vue:81-100`、`FinanceHomeView.vue:138-150`） | **Z3**：orders/payments 加 15~30s 短 TTL 应用级缓存；`useReloadOnActivate` 缓存未过期时**跳过重拉** → 导航来回不再闪、不再反复全表拉 |
| **开单提交卡** | 提交销售单时 `Promise.all(items.map(getStock))` **逐条** `getStock(id)`（N 条独立新加坡往返），已有批量 `stockOf(ids)` 但未用（`src/stores/sales.ts:62-70`） | **K1**：改用 `stockOf(ids)` 批量 → N 请求→1 请求 |

> 说明：经核实**没有真正的"乱跳转死循环"**（路由守卫只在未登录/越权时重定向，属设计行为）。您感知的"乱跳转"主要来自**返回首页重拉造成的闪屏重渲染**，Z3 直接根治。

## 二、系统底座（杠杆点，治本·强烈建议全做）

这 3 项是「一处改动、全站受益」的杠杆，不绑定任何具体业务页：

### Z1 · keep-alive 加内存上限（防卡死）
- **位置**：`src/App.vue:18-20` —— `<keep-alive>` 当前无条件包裹所有非 plain 路由、无 `max`。
- **改法**：`<keep-alive :max="12">`，LRU 淘汰最久未用页面。被淘汰页重进会重新拉数据（符合预期，且 `SalesCreateView` 等已用 `onActivated` 重置，无副作用）。
- **收益**：弱机/长时间使用内存封顶，根治"越用越卡/卡死"。
- **风险**：极低（淘汰=重新加载，体验不变）。

### Z2 · 启动预热商品改窄字段（治打开慢）
- **位置**：`src/db/cloudDb.ts:640-649` `warmUp()` + `src/stores/user.ts:200,216,271,292,305` 调用处。
- **改法**：`products` 预热从 `.toArray()`（全字段）改为 `scanNarrow('id,brand,model,category,spec,unit,warnStock')`（与 `useProductCache` 同口径），其余 5 张小表（customers/suppliers/users/locations/rolePerms）仍全量（量小）。
- **收益**：冷启后那次隐性全量拉取 1.4MB→~0.4MB，手机端打开明显变轻；预热仍够喂商品选择弹层。
- **风险**：低（`useProductCache` 同写法已验证）。

### Z3 · 应用级跨页缓存 + useReloadOnActivate 智能跳过（治乱跳/反复加载）
- **位置**：`src/composables/useReloadOnActivate.ts`（或等价封装）+ 各首页 `reload()`。
- **改法**：
  1. 新增一个轻量 `ordersCache` / `paymentsCache`（模块级 Map + 写入时间戳，TTL 可配，默认 20s）。
  2. `useReloadOnActivate(reload)` 在执行前先查缓存：未过期则**直接复用、不重拉**；过期才真正 `reload()`。
  3. 各首页 `reload()`（销售/采购/财务）优先读该缓存，不再各自 `toArray()` 全表。
- **收益**：导航来回（首页↔详情↔开单）不再每次全表拉 `orders`/`payments`，闪屏消失、流量减半。
- **风险**：中低（需统一缓存键与失效时机；TTL 内他人新增单据需手动刷新——对单人/小团队 ERP 可接受，且现有 `useReloadOnActivate` 本就每次重拉，改后反而更顺）。

## 三、开单（销售 / 采购）

### K1 · 提交销售单库存校验改批量（治提交卡）
- **位置**：`src/stores/sales.ts:62-70` `createOrder` 内 `Promise.all(items.map(it => getStock(it.product.id!)))`。
- **改法**：替换为 `await productStore.stockOf(items.map(it => it.product.id!))`（项目已有批量接口，`product.ts:347-354`）。
- **收益**：10 行明细的提交从 10 个独立跨境往返 → 1 个；行数越多越明显。
- **风险**：极低（复用现成批量接口，逻辑不变）。

### K2 · 调拨 / 盘点进页不再全量（治仓库作业卡死）
- **位置**：`src/views/warehouse/TransferView.vue:200-272`、`src/views/warehouse/CountView.vue:201-274`。
- **改法**：商品选择改走服务端 loader `pickerPage`（与开单选商品同一套，按页 20 条），取消客户端 `:rows` 全量驻内存；`syncLocationStock` 复用库存管理已拉的数据/加内存缓存，避免每次进页重拉。
- **收益**：仓库视角进调拨/盘点页少 1~2 个全表往返、不再把 6281 商品驻内存。
- **风险**：中（需把两页的"全量可选商品"逻辑改成分页/搜索，改动面略大但套路成熟）。

## 四、库存

### I1 · 库存明细 Tab 的 locationStock 窄字段 / 合并
- **位置**：`src/stores/inventory.ts:150-156`(`reconcileProducts`) + `:306-318`(`distributionAll`)，多库位下 `locationStock` 可达 1.2 万行全量。
- **改法**：`scanNarrow` 只取 `productId,locationId,quantity`；或两结果由一次读派生（照搬 `LocationsView` 已验证写法）。
- **收益**：切到库存明细/分布首次加载更轻。
- **风险**：低。

### I2 · 库存管理 商品整表瘦身 + locationStock 去重（即原 V7 F2/F3，并入此处）
- **位置**：`src/views/stock/StockManageView.vue:104` `listAll(false)` 全字段；`:115,118` `locationStock` 拉 2 遍。
- **改法**：商品改 `scanNarrow` 7 列；`locationStock` 合并成 1 次读。
- **收益**：库存管理页每次进页省 ~1MB + 1 往返。
- **风险**：低。

## 五、财务（即原 V7 F1，并入此处）

### F1 · 财务工作台 payments 拉 3 次 → 1 次
- **位置**：`src/views/finance/FinanceHomeView.vue:138-150` + `src/stores/finance.ts:24,67`。
- **改法**：照搬对账页写法——外层拉 1 次 `pays`，透传 `paysAll=pays` / `ordersAll`，`listReceivables(true,paysAll)` / `listPayables(true,paysAll)` 复用，不再各自 `toArray()`。
- **收益**：payments 3 次→1 次、saleOrders/purchaseOrders 各 2 次→1 次。
- **风险**：极低（对账页同写法已上线验证）。

## 八、风险边界（铁律不变）

- **只改**：取数范围 / 字段范围 / 缓存策略 / 内存上限 / 预热口径；**不改**任何业务规则、金额、库存、状态机。
- 每批单独提交 + 单独打 tag，出问题按基线标签回退。
- 验收（数字，不靠感觉）：
  1. 启动后 warmUp 网络传输量下降（1.4MB→~0.4MB，Network 看 `products` 请求体）。
  2. 内存：连续打开 20+ 个不同页面后，浏览器内存不再单调攀升（keep-alive max 生效）。
  3. 导航：首页↔详情↔开单来回 5 次，`orders`/`payments` 全表请求数下降 ≥50%（Z3 生效）。
  4. 开单：10 行明细销售单提交，`getStock` 请求数从 10→1。
  5. 受影响测试全绿 + `npm run build` 0 错 + 电脑/手机各走一遍 进货→入库→销售→收款。
  6. 数据正确：改造后核对一次库存与应收应付金额，与改造前一致。
