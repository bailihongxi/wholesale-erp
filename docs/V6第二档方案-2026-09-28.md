## 二、实施注意点（都是照抄既有范式，无新发明）

1. **#7 必须先核旧数据**：`batchNo` 索引虽在，但要确认线上 `stockRecords` 所有行 `batchNo` 都有值
   （v3 迁移时是否回填过老流水）。上线前用只读脚本核对 `batchNo` 为空的行数，为 0 才切换；
   否则老单据会「按批次查不到」。`revertDoc`（撤单回库存）走同一改动，属于写路径，**单独重点回归**。
2. **#10 先确认 `returnOrders.orderNo` 已建索引**（`db/index.ts`），没有就随本档一起补一个版本号。
3. **#9 会动 `tests/perf-c-parallel.test.ts` 的计数断言**（「三张字典表只读一次」断言的是
   `products.toArray` 次数）——按新实现**校准**断言（只加/只改，不删不放宽），mock 补 `scanNarrow` 方法。
4. **#11 签名向后兼容**：只加可选参数，不传时行为不变（同 `ordersAll` 先例，有现成回归测试模式可套）。
5. 收尾照例：全量单文件 vitest + `npm run build` 0 错 + `tests/stock-cards-v17.test.ts` 版本断言同步。

## 三、开工方式对比（请拍板）

| 方案 | 内容 | 优点 | 缺点 |
|---|---|---|---|
| **A（推荐）** | **一次做完 5 处**，发一个版 `V2.2-1.6`（`2.33.6` / SW `erp-2.33.6`），约 1 人日 | 一次发版成本最低；5 处互不依赖、各自独立可回滚；改法全是照抄已上线写法，风险与第一档同量级 | 单次提交面稍大（约 6~8 个文件），靠逐项测试锁定 |
| B | 先做 #7（收益最大、唯一涉写路径）单独发版，#8~#11 第二批 | 写路径改动单独验收，最稳 | 两次发版、两次部署复验，周期翻倍 |
| C | 暂不做 | 零风险 | 调拨/盘点/出入库详情继续吃全表扫，数据涨了会越来越慢 |

**推荐 A**：5 处全是「只读取数路径」的改法迁移（#7 的写路径部分靠 `revertDoc` 单测+人工回归兜住），
与第一档同风险量级；分批的收益只是心理安慰，成本却是双倍发版。

## 四、验收标准（数字口径，沿用 V6 总案第七节）

1. 出入库单详情 / 撤单：`stockRecords` 请求数 = **1**（原来是该类型全部流水）。
2. 退换货列表 / 调拨列表 / 盘点列表：`products` 不再整表全字段（窄字段后传输量降 ~70%）。
3. 老板报表页：三张基表（saleOrders/payments/purchaseOrders）全页只拉 **1 遍**。
4. 受影响测试文件全绿 + `npm run build` 0 错；电脑端先验证，再部署复验（`sw.js` 显示 `erp-2.33.6`）。
