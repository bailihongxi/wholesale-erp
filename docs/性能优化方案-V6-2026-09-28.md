# 家电批发 ERP · 全站提速推广方案 V6

> 日期：2026-09-28　｜　适用版本：V2.2-1.4 起　｜　状态：**✅ 第一档已开工并上线（V2.2-1.5，2026-09-28）**
> 目标：把 V2.2-1.4 已验证的 P0 三招（**并行化 / 窄字段 / 去 N+1**）从「采购/销售详情页」推广到全站其它页面。
> 不引入任何新架构、不改任何业务规则，纯照抄已生效的写法。

---

## 一、结论先行：可以，而且大部分页面能直接套

V2.2-1.4 已经用实测证明了三招有效（采购/销售详情页 6 次串行往返 → 1 次；商品缓存 1.4MB → 0.37MB；
finance 约 1200 次请求 → 3 次）。对全站 42 个页面 + 主要 store 做了一轮**只读取证**，结论：

- **能直接套用 P0 三招的页面 / 函数：16 处**（含 1 处死代码清理）。
- **已经做对的范本**：入库验货/出库拣货详情、各列表页（`useServerPager` + 服务端分页）、老板工作台首页、
  报价/询价明细（`useProductCache` + `stockOf(ids)` 批量）—— 这些不用动，是范本。
- **不需要动的页面**：登录、我的、设置、员工管理、审计日志、库存详情/预警（数据由父级传入）等，取数已最优或数据量小。

按影响从大到小分三档，**第一档 6 处占了约 80% 的可省耗时**。

## 二、P0 三招（已验证，照抄即可）

| 招式 | 固定写法 | 效果 |
|---|---|---|
| **① 并行化** | 互不依赖的多个 `await` 合成一个 `Promise.all([A(), B(), C()])` | 串行 N 次往返 → 1 次 |
| **② 窄字段** | `db.xxx.toArray()`（全字段）→ `scanNarrow('需要的列')`（云端 SELECT 指定列，本地回退 `toArray()`） | 传输量 -60%~-74% |
| **③ 去 N+1** | 循环里逐条 `await db.xxx.get(id)` → `where('id').anyOf(ids)` 一次批量 + `Promise.all` | 几十~上千次请求 → 1 次 |

## 四、怎么改（不重复发明轮子，全部复用现有工具）

- **并行化**：照抄 `InboundDetailView.vue:291-320` 的 `Promise.all` 现成写法。
- **窄字段**：照抄 `useProductCache.ts` 的 `scanNarrow` + 本地 `toArray()` 回退；商品名一律复用 `useProductCache` 不再 `db.products.toArray()`。
- **去 N+1 / 按批次取**：照抄 `stockDoc.listDocs` 的 `where('batchNo').equals()`（索引已在 `db/index.ts` v3 建好）+ `loadSaleCostBase` 的 `anyOf+bulkGet`。
- **前端页面**：`StockManageView` 改用 `productStore.pickerPage`（服务端分页，和选商品弹层同一套，不再进页面拉全量）。

## 六、风险边界（铁律）

- **不改**：任何业务规则、金额算法、库存增减、单据状态机。
- **只改**：取数的顺序、范围（字段/行数）、缓存策略。
- **不删**：#12 死代码默认不动（用户铁律「不乱删」），如要清理单独拍板。
- **可回滚**：每档单独提交 + 单独打 tag，出问题按基线标签回退。
- 上线节奏不变：**先电脑端验证 → 再推部署 → 手机端复验**。

---

## 七、验收标准（用数字，不靠感觉）

1. **请求数**（浏览器 Network）：报表页 ≤ 4、库存管理页 ≤ 2、退换货详情 ≤ 1。
2. **时间**：同一手机同一网络，改造前后各测 3 次取中位 —— 列表/明细 ≤ 1.2s。
3. **回归**：受影响测试文件全绿 + `npm run build` 0 错 + 电脑/手机各走一遍 进货→入库→销售→收款。
4. **数据正确**：改造后核对一次库存与应收应付金额，与改造前一致。
