### 0.4 贯穿全程的六条硬约束

1. **表结构零变更** —— 全程不动数据库表，只改取数方式与渲染。
2. **一档一 commit 一 tag** —— 坏了一格拆一格，绝不"整包回滚"。
3. **老板账号先灰度** —— 每档先只用老板账号跑全链路（做单 / 编辑 / 删除 / 打印 / 转单），再全量。

## 二、补一个 V2 漏掉的真问题：登录态会被「弱网误踢」

### 2.1 现象

> 用户登录或切换后台时，不是直接进入登录页，而是先跳到系统工作台界面，然后突然跳回登录页
> （或上次切后台时出去的那个界面）。

### 2.2 根因（已定位到具体代码行）

`src/db/cloudDb.ts:202-206`：

```ts
async get(id: number | string): Promise<T | undefined> {
  const { data, error } = await this.client.from(this.name).select('*').eq('id', id).single()
  if (error) return undefined          // ← 网络异常被吞掉，返回 undefined，不抛错
  return data as T
}
```

`src/stores/user.ts:97`：

```ts
if (!row || row.status !== 'active') {   // ← undefined 被当成「账号不存在 / 已停用」
  clearSession()
  currentUser.value = null
}
```

**只要这一趟云端请求因为任何原因失败（弱网、切后台、Supabase 抖动、超时），用户就被判定为"账号无效"直接踢下线。**
而触发场景，恰好就是你描述的那几个。

| 版本 | 表现 |
|---|---|
| 旧版（`validateSessionInBackground`，后台不 await） | `currentUser` 先设后清 → **先渲染出工作台，几百毫秒后突然跳回登录页** |
| 新版（`await validateSession()`，V2.1-2.23） | 同一段判定一行没改 → 误踢照旧，只是把"闪一下"换成了"白屏等一个 RTT" |

### 2.3 顺带排除掉的两个干扰项

- **Service Worker 不是元凶**：`public/sw.js` 里没有 `skipWaiting` / `clients.claim`，新版本安装后不会强刷正在打开的页面。
- **登录成功后的跳转根本不走校验**：`LoginView.vue:137` 的 `router.push` 命中守卫的 `isLoggedIn` 短路，`restoreSession()` 压根不执行。
  所以"登录瞬间跳回登录页"这条路径，V2.1-2.23 那次改动一点没覆盖到。

### 2.4 修法

| 方案 | 改动 | 工期 | 优点 | 缺点 |
|---|---|---|---|---|
| **A（推荐）** | ① 判定语义改成「只有明确 `status !== 'active'` 才踢，`undefined` 一律保持登录」；② 启动路径**不再 await** 该校验；③ 校验挪到「老板停用员工」时（写库后立刻踢）或每 10 分钟静默一次 | ~0.3 人日 | 弱网不误踢 + 首屏 0 等待，一举两得；`cloudDb.get()` 这个"吞错返回 undefined"的语义是全库共用的，修它能防住以后其它调用方 | 需要真去改一处业务语义，要跑通经销商/员工两种登录 |
| B | 登录态改三态机 `unknown → checking → ready`，守卫只认 `ready` | ~1 人日 | 最严谨，任何时刻的状态都明确 | 改动面大，所有读 `currentUser` 的地方都要过一遍 |
| C | 直接删掉启动校验，只留 7 天本地会话 + 写操作前补校验 | ~0.1 人日 | 最省事 | 停用员工最长延迟一个写操作才生效 |

**推荐 A**：它同时修掉了「乱跳」和「白屏」，而且 `undefined` 这个语义错误不止 `validateSession` 一处消费。

## 四、各档「与现系统匹配后的优缺点」

> 这一章只写**落到咱们这个项目上**会怎样。通用benefits不重复。

### P0 · 登录误踢修复（0.3 人日）

**在咱们系统里具体是**：`stores/user.ts` 的 `validateSession` 一处判定 + 两处调用顺序。

| | |
|---|---|
| **优点** | ① 直接消灭你反馈的"乱跳"；② 顺带把 V2.1-2.23 引入的首屏白屏一起消掉（跟 L0 是同一处）；③ 改的是纯读判定，不动任何写路径；④ `cloudDb.get()` 这个"吞错返回 undefined"的语义被修正后，`bulkGet` / `count` 等调用方也一并受益 |
| **缺点** | ① 会改变"账号被停用后多久生效"的行为 —— 从"下次启动立即踢"变成"停用那一刻或 10 分钟内踢"，需要你确认这个延时可接受；② 经销商走 `customers` 表、员工走 `users` 表，两条分支都要验，不能只测员工 |
| **风险** | 低。`undefined`（查不到）与 `status !== 'active'`（明确停用）是两件不同的事，前者在离线时本就不该当结论用 |
| **回退** | `git revert` 该 commit 即可，或直接把 `!row` 改回 `!row` 的旧写法 |

### L0 · 把两处性能回归改回去（0.5 人日）

| # | 改动 | 位置 | 风险 |

| 1 | `await validateSession()` → 后台不阻塞（**与 P0 是同一处，建议合并做**） | `stores/user.ts:213` | 极低 |

### L3 · 首屏拆包（1 人日）

`vite.config.ts` 加 `manualChunks`，把 `supabase` SDK（~120KB）与 `vant`（~60KB）拆出去，
路由本身已经是懒加载（`component: () => import(...)`），拆完只下载当前页。

| | |
|---|---|
| **优点** | ① 首屏 3~5 秒 → 1.5 秒左右，**收益/风险比最高的一档**；② 完全不碰业务逻辑，纯构建配置；③ 与已有的路由懒加载天然契合 |
| **缺点** | ① **`main.ts` 的 `initIdleTasks(router)` 会预取路由分包**，拆包后 chunk 划分变了，预取逻辑必须同步核对，否则可能预取到不存在的文件（白打一趟）或预取了当前页多余的 chunk；② `sw.js` 的 `cacheFirst` 用 `ignoreSearch: true` 匹配，hash 文件名能命中，但**新增 chunk 首次仍要走网络**，冷启动第一次会略慢；③ 拆得不好（比如把公共组件切太碎）反而可能让首屏加载更多文件 |
| **风险** | 低 |
| **回退** | 删掉 `manualChunks` 重构建即可，**一行配置的回退** |

### L2 · 本地数据通（8~12 人日）—— V3 里把风险写实

让读操作先走本地 IndexedDB（~10ms），后台同步云端。

| 子项 | 在咱们系统里的具体做法 |
|---|---|
| 读取走本地 | 列表/详情首读 Dexie，同时后台拉云端 |
| 写操作双写 | 云端成功后再落本地，失败回滚（云端失败则本地也不写） |
| 失效策略 | 写操作 `invalidate()` 对应表；切页静默刷新兜底 |
| 降级开关 | 设置页加「清空本地缓存」；数据异常自动退回纯云端 |

**为什么这一档在咱们系统里代价被低估了**（V2 没写清楚）：

- **本地 Dexie 不是"打开开关"，是"重写一层"**：`src/db/index.ts` 里 `ERPDatabase` 类建好了，
  但 `db = USE_CLOUD ? createCloudDb() : _localDb` —— 云端模式下这个类**完全是空壳**。
  启用本地通，等于要让 `cloudDb` 的 15 个方法（`get` / `bulkGet` / `put` / `add` / `bulkPut` /
  `bulkAdd` / `bulkAddReturningIds` / `delete` / `bulkDelete` / `clear` / `update` / `bulkUpdate` /
  `count` / `toArray` / `queryPage`）全部具备"读写双路径"语义。这是 `cloudDb.ts` 478 行的重写级改动。
- **本地与云端没有版本校验**：记忆里有一条铁律 —— *新字段必先在 SQL Editor 建列，否则 PostgREST 静默失败*。
  一旦本地缓存了旧结构的数据而云端表已升级，会出现"本地有数据、云端写不进去"的静默错误。
  **必须配一个 `schemaVersion` 校验，本地版本落后就整体丢弃重建。**
- **经销商隔离是客户端侧的**：报价单按 `customerId` 过滤。若本地留了别经销商的数据，
  理论上存在泄漏面。虽然实际设备上不会跨账号，但共用电脑上"员工登过再切经销商"是需要防的。

| | |
|---|---|
| **优点** | 唯一能让"查询/编辑/删除/切页"做到无感的方案；断网也能开界面 |
| **缺点** | ① 工期最长（8~12 人日），风险集中在**数据一致性**，错了是账目问题；② 双写会对现有每张表的写路径产生扰动，回归面极广；③ 上面三个坑每一个都能吃掉两天 |
| **风险** | **高** |
| **回退** | 设置页「清空本地缓存」一键退回纯云端读取（这是**必须做**的配套，不是可选项） |

### L4 · 乐观更新（5~8 人日）—— V3 里建议砍一半

保存/删除/确认点击即生效，云端回包后再校正，失败则回滚并提示。

**在咱们系统里必须砍掉的场景**（这是 V3 相对 V2 最重要的修正）：

> 我们做的是**款到发货、严格全款校验**的单据，涉及**金额与库存**。
> 乐观更新一旦回滚失败，用户会看到"界面上这张销售单已保存，其实没保存"——
> 对批发 ERP 来说这是**账目事故**，比慢几百毫秒严重得多。

**所以 L4 只适用于**：纯展示层的状态切换（Tab 高亮、展开/收起、筛选条件回显、
列表排序），**绝不能用于**：保存单据、确认入库/出库、改价、删除、任何涉及金额与库存的操作。

| | |
|---|---|
| **优点** | 做单时点击即响应，体感最好 |
| **缺点** | ① 砍完之后，真正受益的场景只剩"筛选/展开"这类轻量交互，**性价比大幅下降**；② 若与 L2 捆绑，本地数据源在"云端写入失败"时的回滚逻辑复杂；③ **部分改动（已提交到云端的记录）无法真正回滚**，只能提示用户 |
| **风险** | 中（若按上面的边界砍掉，风险可降到低） |
| **回退** | 展示层可 revert；**已经产生云端数据的操作无法 revert**，所以这一档必须"先灰度、观察几天" |

## 七、回滚手册（做坏了的当天就用它）

```bash
# ── 1. 只回退一档（推荐先试这个）───────────────────────
git log --oneline -5                      # 找到该档的 commit
git revert <commit>                       # 生成一个反向 commit
npx vitest run tests/<相关测试文件>.test.ts
npm run build                             # 必须 0 错
# 然后按原流程重新部署

# ── 2. 整个优化全部回退到基线 ────────────────────────
git reset --hard v2.1-2.23-baseline       # 本地
git push origin main --force-with-lease   # 线上（会连带回退 V2.1-2.23 的功能，谨慎）

# 只回退线上、保留本地：
git revert --no-commit ee96300..main && git commit -m "revert: 全部性能优化回退"
git push origin main

# ── 3. 线上出问题、来不及排查 ────────────────────────
# 用基线代码重新构建，按原流程推 gh-pages
git worktree add /tmp/perf-revert v2.1-2.23-baseline
cd /tmp/perf-revert && npm ci && npm run build
# dist 内 git init + checkout -b gh-pages + add -A + commit + push --force
# 之后等 ~75 秒，复验线上 sw.js 的 BUILD_VERSION

# ── 4. 线上最快的退路（不经排查，直接回到 V2.1-2.2）──
# 远程 gh-pages 上的 cbebf98（deploy V2.1-2）仍在，
# 用 git worktree 取出该提交重新推一次即可恢复线上
```

**日常护栏**（每次改完立刻自查）：

```bash
npx vitest run tests/<单文件>     # 本机负载高时不要多文件并行，会被 SIGTERM 杀掉
npm run build                     # vue-tsc -b, noUnusedLocals，0 错才算过
```
